## Deferred from: Epic 16 visitor counter scoping (2026-09-21)

- **No Impressum and no Datenschutzerklärung exist anywhere in the application** [travelblogs/src/app/] — surfaced while scoping the visitor counter, but entirely independent of it. The app is publicly reachable via share links, and the web server logs IP addresses regardless of whether the counter ships, so the disclosure obligations under Art. 13 GDPR and §5 DDG already apply today. Epic 16 is deliberately designed to store no personal data precisely so that it does **not** depend on this being fixed first — but the gap is the larger real exposure and should become its own story. Not a code defect; a product/legal decision for the owner. **Resolved 2026-09-21: promoted to Epic 17 (Stories 17.1 and 17.2), both `ready-for-dev`.**
- **No unique-visitor measurement** [Epic 16 non-goal] — deferred by explicit product decision, not oversight. Would require processing IP addresses or device fingerprints, which the DSK treats as personal data even when hashed, and would therefore need a legal basis plus a privacy notice (see above). Revisit only if page-view numbers prove insufficient *and* the privacy notice exists.
- **No abuse protection on the view beacon** [travelblogs/src/app/api/trips/share/[token]/view/route.ts, once implemented] — the endpoint is unauthenticated by necessity and increments a counter, so anyone holding a valid share token can inflate the number with a loop of requests. Accepted for v1: the figure is informational and visible only to editors. An in-memory, non-persisted per-IP rate limit is the natural follow-up if numbers ever look implausible.
- **Shared map page is not counted** [travelblogs/src/app/trips/share/[token]/map/page.tsx] — explicit Epic 16 non-goal. Trip and entry pages cover the reading surfaces; the map is a navigation aid. Add a third counter only if map usage becomes a question worth answering.

## Deferred from: Epic 17 legal pages scoping (2026-09-21)

- **OpenStreetMap tile transfer is disclosed, not avoided** [travelblogs/src/components/trips/trip-map.tsx:112, travelblogs/src/components/trips/fullscreen-trip-map.tsx:166, travelblogs/src/components/entries/entry-hero-map.tsx:71] — every anonymous reader of a shared trip, entry or full-screen map sends their IP address and User-Agent directly to the OpenStreetMap Foundation, because Leaflet fetches tiles from `tile.openstreetmap.org` in the browser. Epic 17 handles this by disclosing it in the privacy policy, which is the cheap path. The transfer could instead be **avoided**, either by deferring tile loading behind an explicit "load map" click or by proxying tiles through the application server. Both are larger changes and both degrade the reading experience, so they are deferred unless disclosure turns out not to be acceptable.
- **No cookie consent banner** [Epic 17 non-goal] — deliberate, and correct as of 2026-09-21: nothing in the application writes a non-essential cookie, `localStorage` or `sessionStorage` entry, and Epic 16 is specified to keep it that way. Revisit only if a feature introduces non-essential client-side storage or a consent-requiring third-party embed. The auth session cookie is strictly necessary and does not trigger the requirement.

## Deferred from: code review of 16-1-count-page-views-for-shared-trips-and-entries (2026-09-21)

- **Unauthenticated write endpoint has no rate limit — SQLite writer-lock exhaustion.** `POST /api/trips/share/[token]/view` costs two reads plus a write transaction against the single-file SQLite database that also serves every page render. The Epic 16 scoping note accepts *count inflation* from a `curl` loop; it does not cover availability. A loop holding a valid share token can saturate the writer lock for the whole application. Pre-existing acceptance extended, not re-assessed.
- **The client chooses which counter moves.** The beacon's `entryId` is only validated for trip membership — nothing ties it to the page actually rendered, so a stale tab, or a reader on the deliberately-excluded map page, can post arbitrary in-trip entry ids. Per-entry figures are therefore soft even without malice. Subsumed by the accepted abuse surface.
- **`token.sub === "creator"` role fallback lives in production code.** `getUser` in `src/app/api/trips/[id]/route.ts:80-97` grants the `creator` role whenever a JWT's `sub` is the literal string `"creator"` and no `role` claim is present. Story 16.1's AC 9 cascade tests authorize through exactly this path with no `user` row present, so the cascade is proven against an authorization route that cannot occur in production. The cascade behaviour itself is genuinely verified; the test fidelity is not. Pre-existing, not introduced by Epic 16.
- **`views Int @default(0)` is unreachable in `TripView`/`EntryView`.** Every create path passes `views: 1`, so the default never applies today. Any future writer that omits it — a backfill, a Story 16.2 aggregate seed — silently records a view as zero. Correcting it needs a migration for what is currently cosmetic benefit.
- **View counts survive share-link revocation.** Rows are keyed to `tripId`/`entryId`, not to the share link, so revoking a link and issuing a new token carries the old counts into the new link's statistics. Arguably correct (counts belong to the trip), but undecided — resolve when Story 16.2 defines what the displayed figure means.
